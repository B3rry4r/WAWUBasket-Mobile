The admin dashboard inherits the WAWUBasket mobile design system. Reuse every token; do not introduce new colours, shadows, or radii. Designers in Figma should publish a shared library with these tokens at the top of the project.

2. Information architecture

2.1 Layout grid

12-column grid, 1280 px target width, 24 px gutters, 64 px outer page margin. Persistent left rail (240 px) for primary nav. Right rail (320 px) optional for context (audit log, system health, evidence gallery in disputes).

Mirrors the mobile WBHomeAppBar shape: avatar (admin profile), search, notifications, system-health indicator, sign out. Title slot to the left of the search field holds the current section name.

5. User management

5.1 Users list

Searchable / filterable table of every account. Columns: ID, Name, Phone, Role(s), Joined, Status, Last seen. Filters: role, status, country, KYC tier.

5.2 User detail

Header card with avatar + name + role pills. Tabs:

  • Profile: identity fields, KYC docs preview, change-history.
  • Orders: full order history, links to each.
  • Wallet: balance, top-up history, withdrawal history.
  • Disputes: any disputes raised or against this user.
  • Activity: device fingerprints, login locations, suspicious flags.

6. Approvals

Five symmetrical screens (one per operator role). Same layout, different document set per role.

6.1 Approvals queue layout

Left rail of tabs: Vendor (V), Trader (T), Agent (A), Rider (R), Driver (D). Each tab shows count badge. Body = filterable table + detail drawer.

6.2 Approval detail drawer

Slides in from the right. Three sections:

  1. Identity: name, phone, business, region, date of application.
  2. Documents: tiled previews + download. Each tile shows OCR-extracted text and a confidence badge (auto-verified, needs review).
  3. Bank verification: resolved account name + match against KYC name; mismatch flagged in red.

Footer actions: Approve Decline (with reason) Block (with reason).

8. Disputes & escrow

8.1 Dispute queue

Table grouped by status: Open, Under review, Escalated, Resolved. Columns: dispute ID, order ID, party who raised, reason, age, escrow held, assigned admin.

8.2 Dispute thread

Chronological timeline: customer message, vendor reply, rider note, admin notes. Photo gallery with zoom for evidence. Order timeline rendered top-down (Paid → Held → Awaiting delivery → Confirm receipt).

8.4 Escrow ledger

Read-only ledger of every escrow movement: held, released, refunded, disputed, adjusted. Mirrors the buyer-side Bulk orders screen but with admin annotations + manual-adjustment trail.

9. Financial reconciliation

9.1 Reconciliation dashboard

Three KPI tiles (Total held / Bank balance / Difference) on a hero card. If |difference| > ₦10,000 the tile flashes statusError red and an alert is emitted.

9.2 Payouts

List of every payout grouped by status. Bulk actions: hold, release, retry. Each row has an idempotency key (UUID) shown in a copy chip — duplicate requests use the same key.

9.3 Currency conversion

Read-only feed of the FX rates pulled from the conversion service every 5 minutes (NGN ↔ XOF ↔ XAF). Spread is 2.5% — surfaced as a column. Designer note: chart with sparkline per pair.

9.4 Manual escrow adjustment

Restricted modal. Fields: order ID, amount, direction (buyer↑ / seller↑), reason (required), admin signature. Posts an audit entry, locks the row for 24 hours from further adjustment.

10. Audit log

10.1 Layout

Single screen, table-first. Filters across the top (admin, action, entity, date range, IP). Columns: timestamp (with timezone), admin name, action, entity, IP, diff (collapsed, expandable).

10.2 Detail row

Expanding a row shows the JSON diff (before / after) of the affected entity, with each changed key highlighted. Read-only.

10.3 Export

CSV export of the current filter set. Streamed to S3 then surfaced as a signed-URL toast.

11. Monitoring & alerts

11.1 Service health board

Grid of service tiles (API gateway, escrow service, dispatch service, tracking websocket, transactional email, push notification). Each tile shows uptime %, p95 latency, error rate.

11.2 Live transaction volume

Real-time line chart pulled via WebSocket (/admin/metrics/live). Two series: orders/min and ₦ volume/min. 60-minute rolling window.

11.3 Alert configuration

Rules table. Each rule: metric, operator, threshold, window, recipients (Slack, email, SMS). Boilerplate set: error-rate > 1% for 5 min, p95 latency > 1s for 10 min, payout failure > 3 in 1h.

11.4 Backup management

List of automated daily PostgreSQL dumps shipped to S3. Manual trigger button (restricted to Super Admin). Restore is operator-led — surface a "Request restore" workflow that opens a ticket; do not expose restore from the UI.

12. Government data portal

Sub-portal of the admin dashboard, white-labelled per agency (NEPC, Customs, NAFDAC). Authentication is API-key + IP whitelist, not the admin SSO. Visually subordinate to admin but uses the same design system.

12.1 Dashboard

Filter set across the top: corridor, date range, products. Below:

  • Four metric cards (Total trade volume, Total trade value, Active shipments, Active traders).
  • Trade-volume trend chart (Chart.js line).
  • Top-products bar chart.
  • Border-activity heatmap (Mapbox border-markers with bubble radii proportional to volume).

12.2 Reports

Self-serve report generator: type (monthly / quarterly / annual), corridor, products, format (PDF / CSV), schedule (one-off / monthly recurring). PDFs use the same Inter / monochrome look as this guide.

12.3 API keys

Create / revoke API keys per agency. Each key has expiry, IP whitelist, scope (corridor, product), rate limit. Show usage in a sparkline per key.

12.4 STR / policy

Two pushed pages reached from the data portal:

  • STR sync: last successful push timestamp, manual re-push button, recent payload preview.
  • Policy simulator: three sliders (checkpoint count, fuel price, road-closure days). Right side shows projected trade-volume change, before/after lines, "Generate PDF report" button.

13. Content reference

Reuse the brand voice guide verbatim where possible. Below is the canonical copy palette for admin surfaces.

Tone

Calm, accurate, low-drama. Admin copy must read like an internal operator's notebook: short headings, factual descriptions, no marketing language. Avoid em dashes; use commas or full stops. Status pills are the visual carrier of emotion — let them do that work.

14. Acceptance criteria

  1. Every screen uses tokens from §1. No bespoke colours, shadows, or radii.
  2. Every destructive action (suspend, refund, manual adjustment) requires a reason and writes a deterministic audit entry.
  3. Every admin write endpoint sits behind RBAC; designers should denote the required role on the Figma frame note.
  4. Every long-running list (users, orders, audit) supports cursor pagination with a 20-row default and a per-row anchor (`?after=…`).
  5. Every detail surface has a "Last edited by" footer attribution drawn from the audit log.
  6. Every numeric value is rendered with tabular-nums and the Naira symbol prefixed (no postfix); FX-converted values show original + converted side by side.
  7. The government portal is visually separate but design-system identical — agency branding lands in the header avatar only.
  8. Mobile breakpoints: 1024 px collapses the left rail into a hamburger; 768 px folds tables into card lists. The admin app is desktop-first; below 768 px is read-only.
